# Поиск претендентов на разработку — постоянная инструкция

**Дата начала:** 31.10.2026  
**Актуальный статус (01.11.2026):** F1-015 завершена, 225 успешных Wordstat GetTop (165 числовых, 60 без числа), 208/270 исходных Q1/Q2 и 17 дополнительных R-фраз. Все 135 сценариев первично исследованы, но все 135 CLARIFY (0 PASS/REJECT). Архив F1-010 исторически восстановлен лишь частично. Старые PREPARED_NOT_EXECUTED в хронологии ниже могут быть неактуальны.
**Рынок:** Россия, русскоязычные пользователи.  
**Назначение:** постоянная память исследования и инструкция для любого следующего ChatGPT-диалога.

## 1. Зачем существует этот проект

Владелец выдвинул бизнес-гипотезу: благодаря ИИ разработка простых программ, утилит, ботов, небольших веб-сервисов и браузерных расширений стала существенно доступнее. Многие реальные потребности раньше оставались без хорошего коммерческого решения не потому, что их технически нельзя было удовлетворить, а потому, что потенциальных покупателей было слишком мало относительно стоимости разработки и сопровождения.

**Наша задача — систематически находить на российском рынке такие небольшие неудовлетворённые или недостаточно хорошо обслуживаемые потребности и оценивать, какие из них экономически целесообразно превращать в самостоятельные микропродукты.**

Два особенно интересных типа кандидатов:
1. **Одна полезная функция дорогого или сложного большого продукта.** Человеку нужен конкретный результат, а ради него приходится покупать, внедрять или осваивать целую CRM, ERP, систему документооборота, управления складом, производством, аналитикой и т. п.
2. **Специфическая задача узкой аудитории.** У небольшой профессии, категории предпринимателей или пользователей есть повторяющаяся проблема, ради которой раньше никто не создавал отдельный продукт.

Третий смежный тип — небольшая повторяемая ручная операция: превращение, сверка, переименование, печать, группировка и проверка файлов или данных.

**ИИ здесь прежде всего средство удешевления разработки.** Будущий продаваемый продукт не обязан использовать ИИ: надёжная детерминированная утилита зачастую лучше.

Это исследование рынка, **не** приказ немедленно разрабатывать каждую идею; **не** поиск исключительно ИИ-ботов; **не** проект по разработке самого Yandex Marketing Bridge.

## 2. Главный принцип поиска

Мы ищем **проблему пользователя и минимальный законченный полезный результат**, а не просто слова «программа», «бот», «автоматизация».

Пример: человек не хочет внедрять систему закупок. Он хочет загрузить два прайс-листа и увидеть изменившиеся цены. Или ему нужен один инструмент для расчёта материалов конкретного изделия, а не комплексная производственная система.

Исследовать нужно и коммерческие, и проблемные формулировки:
- «программа для ...», «бот для ...», «сервис ...»;
- «как автоматически ...», «как массово ...», «как сравнить ...»;
- «из excel в ...», «перенести ...», «сверить ...»;
- «без 1с», «без crm», «без подписки», «дешевле ...»;
- «калькулятор ...», «учёт ...», «сформировать ...», «печать ...».

Одна и та же потребность может иметь много запросов. **Единица анализа — задача/ниша, а запросы — сигналы о ней.** Не считать каждую словоформу отдельным рынком.

Привлекательность складывается из реальности проблемы, частоты/дороговизны ручной работы, платежеспособности аудитории, недовольства альтернативами, себестоимости разработки, дальнейшей поддержки, юридических рисков и доступности каналов продаж. **Малая частотность сама по себе не означает хорошую нишу**; большая частотность не равна числу покупателей.

Основной инструмент первичного изучения формулировок и спроса — **Яндекс Wordstat через браузерное расширение Yandex Marketing Bridge**. Дополнительно используем Yandex Search через тот же Bridge для изучения результатов поиска и конкурентов; при необходимости официальные страницы продуктов, их цены, тематические обсуждения и другие проверяемые источники.

- Репозиторий разработки Bridge: **MaksimUnimax/Yandex_direct**.
- Эта папка — **долговременное исследование**, поэтому хранится на верхнем уровне репозитория, а не в рабочем каталоге work/, предназначенном для временных заказов.
- Предоставленный владельцем ZIP **Yandex Marketing Bridge 0.1.14 (ChatGPT Chat FIX)** проанализирован 31.10.2026; он не доказывает, что такая версия находится в main или установлена у владельца. В доступном на момент создания этой инструкции main manifest указывал 0.1.1. Перед реальными командами сверить текущую установленную версию и фактический контракт.
- В версии 0.1.14 подтверждены исходниками протоколы **WORDSTAT_API_V1** с методами getTop, getDynamics, getRegionsDistribution, getRegionsTree и **WORDSTAT_BATCH_API_V1** с действиями start, next, status, pause, resume, cancel.

Начинать с небольших пакетов, контролировать число запросов и оценочную стоимость; не отправлять платные запросы без согласованного объёма.

В ручном режиме владелец запускает подготовленные ChatGPT команды кнопкой «Яндекс»; результаты затем передаются в диалог для обработки и сохранения. Если доступны другие проверенные режимы, они используются только в разрешённых пределах.
- Не изобретать схемы API-команд, не симулировать ответы Wordstat и не выдавать предположения за статистику.

## 4. Процесс исследования, который надо повторять для всех кандидатов

**Этап A. Формируем гипотезу.** Описываем, у кого болит, что человек делает вручную, как выглядит минимальная полезная функция, какие решения уже есть и почему их может быть неудобно или дорого использовать. Присваиваем постоянный ID (C001, C002 и т. д.). Начальный список — в РЕЕСТР_ГИПОТЕЗ.md.

**Этап B. Собираем семейство запросов.** Для каждой задачи формируем основные, синонимичные, разговорные, профессиональные, проблемные и явно коммерческие формулировки. Не ограничиваемся словом «программа». Отмечаем неоднозначные фразы, которые могут относиться не к нашей задаче.

**Этап C. Измеряем в Wordstat.** Сначала небольшая первичная партия запросов через getTop/WORDSTAT_BATCH_API_V1; затем для перспективных — динамика (getDynamics), региональные различия и уточнённые формулировки. Начальная география — Россия (в исходниках Bridge для getTop по умолчанию regions [«225»]); устройства — все, если не обоснован иной срез. Фиксировать дату, метод, исходную фразу, регион, устройства, параметры, фактический ответ и ограничения. Проверять значение операторов соответствия отдельно, прежде чем делать выводы об «точной частотности». Числа из пересекающихся запросов **не суммировать как уникальный спрос**. Частотность — не число покупателей, не выручка и не доказательство готовности платить.

**Этап D. Проверяем предложения и конкурентов.** Для обещающих ниш изучаем поисковую выдачу, бесплатные решения, Excel-шаблоны, маленькие сервисы, возможности существующих крупных продуктов, цены и условия. Отличаем «решение отсутствует» от «мы его не нашли». Записываем URL, дату, цену, проверяемую функцию, ограничения и источник. Важно определить: можно ли приобрести именно нужную функцию отдельно? Для дорогих комплексных продуктов указывать, за какую ненужную функциональность пользователю пришлось бы платить.

**Этап E. Проверяем экономику и реализацию.** Описываем MVP, что в него **не входит**, основные входы/выходы, технические зависимости и сложные случаи; оцениваем разовую разработку, поддержку и цену как **гипотезы**, пока нет подтверждения. Учитываем платёжеспособность, частоту использования, стоимость получения клиента, конкуренцию, юридические ограничения и риск превратить «маленькую функцию» в бесконечную интеграционную разработку.

**Этап F. Сравниваем и принимаем решение.** Каждой нише присваиваем статус и степень уверенности; составляем короткий список с доказательствами «за/против». Решения: ИССЛЕДОВАТЬ / ПРОВЕРИТЬ КОНКУРЕНТОВ / ПРОВЕРИТЬ ГОТОВНОСТЬ ПЛАТИТЬ / КАНДИДАТ НА MVP / ОТЛОЖИТЬ / ОТКЛОНИТЬ. **Разработка начинается только после отдельного решения владельца.**

**Этап G. Продолжаем цикл.** Сохраняем новые данные, уточняем старые оценки, сравниваем похожие идеи, отмечаем изменения спроса и цен, расширяем список гипотез. Работа не ограничивается первым поиском или одним отчётом.

## 5. Как сравнивать кандидатов

Оцениваем отдельно, без искусственных баллов при отсутствии данных:
1. **Доказательства потребности:** что именно люди хотят сделать, какие у них потери времени/денег.
2. **Поисковый спрос:** объём, уточнения, динамика, сезонность, регион; качество связи запросов с задачей.
3. **Готовность платить:** факты покупки или платежей при наличии; иначе только проверяемая гипотеза и цена теста.
4. **Пробел существующих решений:** нет подходящего решения, слишком дорогой пакет, сложность внедрения, недостаток конкретной функции.
5. **Размер и чёткость MVP:** одна понятная задача, определённые вход/выход, не слишком много исключений и интеграций.
6. **Экономика:** ориентировочная разработка + сопровождение + канал привлечения относительно потенциальной выручки.
7. **Риски:** персональные данные, доступы к чужим сервисам, зависимость от изменчивых API/интерфейсов, ответственность и правовые ограничения.

Для подтверждённых критериев можно выставлять сравнительные оценки от 1 до 5 с объяснением, а при отсутствии данных — **НЕТ ДАННЫХ** (не ноль). **Общую сводную оценку без достаточных фактов не выдавать за объективный рейтинг.** Кроме оценки указывать степень уверенности: низкая/средняя/высокая, и основания. Главный результат — сравнение выгод, рисков и недостающих фактов, а не один красивый балл.

По возможности проверять **одинаковые критерии и сопоставимые регионы/периоды** для всех кандидатов. Разные даты, методы, устройства и уровни соответствия запросов должны быть явно обозначены.

## 6. Правила фиксации данных в GitHub

Эта папка — источник истины исследования:
- **README.md** (этот документ) — цели, методика, состояние, правила передачи между диалогами.
- **РЕЕСТР_ГИПОТЕЗ.md** — кандидаты и стартовые поисковые фразы; гипотезы, не подтверждённые Wordstat.
- **ШАБЛОН_КАРТОЧКИ_НИШИ.md** — одинаковая структура подробного анализа каждой перспективной идеи.
- **ЖУРНАЛ_ИССЛЕДОВАНИЯ.md** — что сделано, когда, откуда взяты данные, чего не хватает, что делать дальше.
- По мере необходимости создаём вложенные каталоги **данные/YYYY-MM-DD/** (исходные и нормализованные наборы, в т. ч. CSV/JSON с источником и параметрами), **кандидаты/C001/** (карточки и материалы конкретной идеи) и **сравнения/** (общие сравнительные таблицы, выводы и их версии). Git не хранит пустые папки, поэтому они появятся при первом реальном файле.

Для каждого подтверждаемого утверждения сохранять источник: реальный ответ/API-операцию или URL, дату, параметры выборки, метод обработки и ограничения. Чётко маркировать **ГИПОТЕЗА / ИЗМЕРЕНО / ПРОВЕРЕНО / НЕИЗВЕСТНО / ОПРОВЕРГНУТО**. Хранить исходные фактические данные отдельно от интерпретации; исходные данные не подменять красивыми таблицами. Если ответ частичный, записывать частичность. Не сочинять отсутствующие значения, цены и доступность.

Здесь хранить только безопасные публичные исследования и обезличенные данные. Перед сохранением потенциально конфиденциальных материалов согласовать с владельцем другое, приватное хранилище. Если новый диалог не знает предыдущего обсуждения, владелец может сказать:

**«Открой GitHub MaksimUnimax/Yandex_direct, папку „Поиск претендентов на разработку“. Прочитай README.md, реестр гипотез, журнал и последние карточки, затем продолжи исследование с последнего подтверждённого шага. Не начинай проект заново».**

Действия ассистента:
1. Открыть **актуальную** ветку и файлы этой папки через GitHub, не полагаться на память о старом коммите.
2. Прочитать README, реестр, журнал и имеющиеся результаты/сравнения; выяснить текущий этап и точные незакрытые вопросы.
3. Установить, какие команды Wordstat реально выполнялись, какие результаты сохранены и какие неизвестны. **Не повторять платные вызовы без необходимости и согласия.**
4. Проверить текущие возможности установленного у владельца Yandex Marketing Bridge перед генерацией новых команд, отличать GitHub-исходники от установленной версии.
5. Продолжить с последнего незавершённого этапа, задавая владельцу вопросы лишь при действительно необходимом решении.
6. Писать выводы простым русским языком, показывать цифры с источником и отделять факты от оценок.
