# 09 — Черновик сообщения клиенту

Здравствуйте!

Подготовлен исправленный клиентский комплект анализа семантики и структуры сайта `okno-msk.ru` под обычный поиск Яндекса с отдельной bounded диагностической проверкой Search-vs-AI.

После дополнительного независимого методического review пакет был доработан именно в части практического использования: теперь основные результаты доступны не только как внутренние аналитические таблицы, но и как физический клиентский workbook + отдельный читаемый отчёт.

Рекомендую смотреть материалы в таком порядке:

1. **`STEP_19_CLIENT_REPORT_CORRECTED.pdf`** — самостоятельный клиентский отчёт: главные выводы, архитектура, P1-действия, ограничения, execution calibration и measurement logic.
2. **`STEP_19_CLIENT_WORKBOOK_CORRECTED.xlsx`** — основной рабочий файл для клиента/исполнителя.
   - `02_Page_Model` — 15 основных направлений и текущие роли страниц;
   - `03_Semantic_Core` — фактически материализованные 2332 active phrase → task → page rows; ручной JOIN внутренних файлов не требуется;
   - `04_Search_vs_AI` — все 8 проверенных bounded cases;
   - `05_Page_Actions` — что менять, что сохранять и чего не делать без stronger evidence;
   - `06_Source_Obs` — только реально наблюдённые Search/AI sources/competitor observations;
   - `07_Priority_Plan` — аналитическая приоритетность;
   - `Execution_Calibration` — 112 точных work packages с полями owner/effort/capacity/timing для реальной калибровки;
   - `Measurement` — implementation acceptance, baseline, future metric sources, observation window и decision rule по 7 measurement classes.
3. **`STEP_19_CLIENT_REPORT_CORRECTED.docx`** — редактируемая версия того же самостоятельного отчёта, если нужен внутренний review/комментарии перед фактической отправкой.
4. Repo-native Markdown/TSV/JSON остаются supporting/audit layer и не требуют от клиента реконструировать основной результат.

Важное пояснение по приоритетам: **P1/P2/P3 — это порядок аналитической важности, а не готовый календарь разработки.**

Исправленный workbook теперь не просто говорит, что нужна калибровка. В `Execution_Calibration` есть отдельная строка на каждый из 112 work packages. Если реальные значения ещё неизвестны, поля сохраняются как `TO_CALIBRATE`, а не угадываются.

Для production sequence исполнитель/клиент должен заполнить реальные:

- implementation owner;
- effort;
- capacity;
- зависимости/технические ограничения;
- при необходимости подтверждённый внутренний business priority;
- observation window / measurement constraints.

Только после этого аналитическую очередь можно честно превратить в NOW/NEXT/LATER, sprint или календарный sequence.

Часть задач помечена **HOLD**. Это не «не делать» и не «низкая ценность»: 20 точных HOLD packages заблокированы конкретно названными evidence/business/policy gaps. Они возвращаются в приоритизацию только после закрытия своего named blocker.

AI-часть имеет строго ограниченную роль: проверено 8 конкретных запросов. Она помогла подтвердить несколько существующих границ и выделить bounded content recheck/expansion candidates, но не используется как доказательство общей AI-видимости сайта, долгосрочной стабильности или бизнес-эффекта.

В correction также добавлен отдельный measurement layer. Он не обещает рост позиций/трафика/лидов и не выдумывает KPI. Для каждой категории работ сначала определяется **что считается корректным внедрением**, затем — какой baseline и какие Search/business signals можно использовать, если соответствующие first-party данные будут реально доступны и авторизованы.

Главный практический следующий шаг после ознакомления с материалами:

1. открыть `05_Page_Actions`;
2. затем `Execution_Calibration`;
3. передать exact packages реальному исполнителю для заполнения owner/effort/capacity/dependencies;
4. только после этой калибровки сформировать production sequence;
5. использовать `Measurement` для проверки внедрения и будущих сигналов результата.

Если при review выяснится, что бизнес-условия, ассортимент или технические ограничения отличаются от публично доступных данных, такие уточнения нужно внести как явный revision input и пересчитать только затронутые решения, сохраняя историю/lineage анализа.
