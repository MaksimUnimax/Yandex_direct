## 8. Relevant prior errors/corrections

### 8.1 Draft message is not handoff

The Step19 delivery message is explicitly a draft. Its existence cannot prove distribution, receipt, review or acceptance.

```text
DELIVERY MESSAGE PREPARED != PACKAGE DISTRIBUTED
PACKAGE DISTRIBUTED != RECEIVED
RECEIVED != REVIEWED
REVIEWED != ACCEPTED
```

**Non-repeat control:** distinct handoff states and evidence for every transition.

### 8.2 Fresh at QA time is not fresh at handoff time

Step20 created a Level2 freshness window and event-triggered expiry.

```text
STEP20 PASS != TIMELESS HANDOFF AUTHORIZATION
```

**Non-repeat control:** Step21 begins execution with a handoff-time freshness gate. Expiry or an event trigger blocks distribution until the affected Step20 current-site checks are refreshed.

### 8.3 Old QA verdict does not cover a changed version

A revision that materially changes analytical content or client-facing package truth cannot inherit the old Step20 PASS.

**Non-repeat control:** every accepted revision receives an impact class; material mutation creates a new release identity and invokes the specified upstream correction/re-QA route before redistribution.

### 8.4 Analyst scenario validation is not real recipient acceptance

This job is a mock rehearsal. Step20 correctly did not claim real external user validation.

**Non-repeat control:** all Step21 rehearsal states are prefixed/typed as SIMULATED_TEST_DEMO where no real external recipient exists. `CLIENT_ACCEPTED` is forbidden without actual evidence from a real authorized client/commissioner.

### 8.5 Analytical priority is not a production schedule

Handoff must preserve `PENDING_CALIBRATION` for owner/effort/capacity and must not convert P1/P2/P3 into a promised sprint/calendar.

### 8.6 Research read is not requirement operationalized

Step20 established that research can be correct yet still fail if requirements remain narrative.

**Non-repeat control:** every Step21 research finding is mapped to an execution operation, saved state/evidence, transition consequence and QA gate in `STEP_21_RESEARCH_TO_EXECUTION_SCHEMA.tsv`.

## 9. Fresh external method research

### 9.1 AQuA Book 2025 — delivery, communication and sign-off

Source: https://www.gov.uk/guidance/the-aqua-book

Classification: **OFFICIAL / PRIMARY ANALYTICAL ASSURANCE GUIDANCE**.

Material requirements extracted:

- delivery communicates insights, assurance state and limitations so the commissioner/approver can judge fitness for use;
- commissioner, analyst, assurer and approver roles are distinct;
- sign-off is evidence-bearing approval, not inferred from file delivery;
- supporting documentation and assurance evidence should be ready at handover;
- further iteration/analysis/assurance may be required after commissioner review;
- robust version control is required so changes can be seen and assured.

### 9.2 Government Functional Standard GovS 010 — Analysis

Source: https://www.gov.uk/government/publications/government-analysis-functional-standard--2/government-functional-standard-govs-010-analysis

Classification: **OFFICIAL / PRIMARY GOVERNANCE GUIDANCE**.

Material requirements extracted:

- expectations and scope must remain aligned with commissioner needs;
- analytical outputs pass through sign-off rather than being treated as accepted merely because production is complete;
- assurance and governance should be proportionate to use/risk.

### 9.3 UK Government contract-management change-control guidance

Source: https://www.gov.uk/government/publications/civil-service-helping-you-with-managing-suppliers-and-contracts/contract-management-training-accreditation-foundation-level-takeaway-guide-html

Classification: **OFFICIAL / CHANGE-CONTROL PRACTICE**.

Material requirements extracted:

- keep change records retrievable;
- use version control on key documents;
- involve/obtain the required stakeholder sign-off;
- do not make informal changes simply because they look small;
- update the controlled baseline/audit trail after an approved change.

### 9.4 PMI scope change control

Sources:

- https://www.pmi.org/learning/library/scope-control-projects-you-6972
- https://www.pmi.org/learning/library/scope-management-9099

Classification: **INDUSTRY PRACTICE**.

Material requirements extracted:

- change is expected but must be controlled;
- a request must be defined and its impact analysed before approval;
- approval authority must be explicit;
- only approved changes update the baseline;
- change control should be structured but not burdened by unnecessary bureaucracy.

### 9.5 PMI handoff/closing practice

Source: https://www.pmi.org/learning/library/proactive-intervention-resolving-project-problems-137

Classification: **INDUSTRY PRACTICE**.

Material requirements extracted:

- manage acceptance against agreed criteria;
- consolidate/validate project documentation;
- prepare turnover/handoff documentation;
- close open items before contractual/project close;
- handoff and closure are separate lifecycle events.

### 9.6 GitHub immutable release/integrity guidance

Sources:

- https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases
- https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity

### Phase C — recipient/review state

10. Use explicit acceptance criteria rather than treating silence or file availability as acceptance.
11. For Mode A rehearsal, run a simulated recipient checklist against the physical package and mark all results `SIMULATED_TEST_DEMO`.
12. Do not create `CLIENT_ACCEPTED` or `REAL_USER_VALIDATED` states.

### Phase D — revision intake and change control

13. Every revision input gets a unique ID, exact request text/summary, source, timestamp, requested outcome and affected deliverable/scope.
14. Classify before editing:
    - `CLARIFICATION_ONLY` — explanation, no baseline mutation;
    - `COSMETIC_PRESENTATION` — formatting/wording with no analytical meaning change;
    - `NON_MATERIAL_CONTENT_CORRECTION` — factual/edit correction with bounded re-QA;
    - `MATERIAL_ANALYTICAL_REVISION` — changes an action, page role, semantic mapping, priority claim, limitation or other analytical conclusion;
    - `SCOPE_CHANGE_NEW_REQUIREMENT` — changes frozen commission/region/output/business requirement;
    - `FRESHNESS_TRIGGER` — site/business state may have changed and current-world evidence must be refreshed.
15. Perform impact analysis before approval: affected steps, affected files/claims, evidence needed, QA invalidation, provider need, cost/scope consequences.
16. Record disposition: `APPROVED`, `REJECTED`, `DEFERRED`, or `NEEDS_CLARIFICATION`.
17. No approved change may be silently applied outside the revision ledger.

### Phase E — version and re-QA

18. Clarification-only response does not create a new analytical release.
19. Any package mutation receives a new explicit version identity; the previous distributed version remains preserved/auditable.
20. Material analytical revision reopens the exact upstream authority and requires downstream regeneration/re-QA; a materially changed package requires a fresh Step20 release-assurance verdict.
21. Provider acquisition remains zero by default. If a revision genuinely requires new provider evidence, stop for separate provider authorization and preservation gates.

### Phase F — revision closure and Step22 transition

22. A revision is closed only after disposition, required correction, re-QA and any required redistribution are complete.
23. Step21 is complete only when no accepted/open revision remains, current distributed-version truth is explicit, and the rehearsal acceptance/handoff state is recorded without false real-client claims.
24. Step22 is allowed only after those conditions are read back from GitHub.
