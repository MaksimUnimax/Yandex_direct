## 12. Step19 adversarial self-audit before execution

### Attack: “Why not just export all internal TSVs?”

Because raw internal artifacts optimize auditability, not client comprehension. External reporting practice requires actionable/contextual communication. The client layer must summarize while preserving detailed traceability behind it.

### Attack: “Why not manually write each file for maximum readability?”

Because independent manual copies create contradiction risk. One canonical data model must feed all views.

### Attack: “Why not tell the client P1 is what to implement first?”

Because Step18 proves analytical importance, not a committed production schedule. Missing owner/effort/capacity blocks the stronger claim.

### Attack: “Why not use 112 work packages as the executive action list?”

Because it would recreate a technical backlog in the summary. Client-facing grouping is allowed, but exact package traceability must remain available.

### Attack: “Why not hide HOLD to make the report cleaner?”

Because HOLD is a real unresolved decision boundary, not noise. Hiding it would turn uncertainty into an unsupported recommendation/no-action claim.

### Attack: “Why not generalize the eight AI cases into overall AI visibility?”

Because exact-query bounded snapshots do not prove sitewide visibility or longitudinal stability.

### Attack: “Why not add a fresh competitor audit while building deliverable 06?”

Because Step19 is a packaging stage. `SOURCE_COMPETITOR_OBSERVATIONS` must report accepted observations, not silently expand scope with a new acquisition/analysis stage.

### Attack: “Why not finish Step20 QA inside Step19?”

Step19 needs its own construction QA, but Step20 is an independent final reconciliation gate. Collapsing them removes the independent review layer.

## ПРОСТЫМИ СЛОВАМИ — ЗАЧЕМ / ЧТО / РЕЗУЛЬТАТ

**Зачем нужен Step19:** все основные решения уже получены, но сейчас они разложены по множеству технических файлов. Клиент не должен разбираться в наших внутренних таблицах, ID и этапах, чтобы понять результат работы.

**Что будем делать после разрешения:** соберём из уже подтверждённых данных один согласованный клиентский набор. Сначала создадим единую основу, чтобы одна и та же страница или рекомендация в разных документах всегда означала одно и то же. Затем из неё сделаем краткое понятное резюме, карту направлений и страниц, полный семантический workbook, таблицу Search-vs-AI, карту конкретных действий, наблюдения по источникам/конкурентам, план аналитических приоритетов, описание метода/ограничений и готовый текст сообщения клиенту.

**Что получим:** девять согласованных клиентских материалов, где понятно, что найдено, что менять, почему, что важнее, что пока неизвестно и на каких данных всё основано. При этом мы не будем выдавать аналитическую важность за календарь внедрения, а ограниченную AI-проверку — за общую видимость сайта в AI.
