# 08 — Метод и ограничения

Дата: 2026-09-03  
Режим: **публичный базовый анализ + сохранённые Wordstat/Search/GenSearch evidence; без клиентских Webmaster/Metrika/Direct данных**

## Что было использовано

Работа соединяет несколько независимых типов доказательств:

- текущий публичный сайт и текущие страницы — чтобы понять реальный ассортимент, роль страниц, содержание и переходы;
- Yandex Wordstat — как сигнал человеческого спроса и словаря запросов;
- обычную выдачу Yandex — чтобы проверять пользовательскую задачу, типы результатов и границы между страницами;
- текущую карту сайта/страниц после повторной проверки — чтобы не рекомендовать отсутствующие или уже существующие страницы по старому snapshot;
- ограниченную выборку GenSearch — только для 8 заранее выбранных диагностических запросов;
- аналитическое сопоставление ChatGPT — для группировки задач, выбора intended page owner, архитектурных действий, ограничений и приоритетов.

## Как читать Wordstat

В семантическом ядре сохранены реальные provider counts и provenance из принятой Wordstat-выборки. Broad provider count не переименовывается в «точную частотность», если точный оператор не использовался.

```text
WORDSTAT OBSERVED COUNT
!= GUARANTEED EXACT QUERY FREQUENCY
```

Поэтому число показывает относительный/наблюдаемый спрос в рамках использованного запроса и настроек, а не обещанный точный объём будущих показов или визитов.

## Как читать page ownership

`target_url` / primary page означает страницу, которая по принятому анализу должна отвечать данной задаче пользователя.

Это не означает автоматически:

- что именно эта страница сейчас ранжируется по каждой фразе;
- что её позиции хорошие;
- что она не требует контентной доработки;
- что Yandex Webmaster подтвердил query→URL association.

Клиентские private Webmaster данные в этом тесте не использовались.

## Как читать обычный Search

Обычная выдача Yandex использовалась как наблюдение того, какие задачи и типы страниц Yandex показывает по конкретным запросам. Search evidence помогала различать, например, material-led и use-case-led задачи, narrow specialist и broad owner, commercial и informational responsibility.

Одна выдача не доказывает историческую стабильность или причинный вред от конкурирующих страниц.

## Как читать AI-часть

AI-часть — **8 exact-query диагностических кейсов**, а не репрезентативная выборка всего сайта.

Итог:

```text
CHANGE = 0
DE_RISK = 4
NO_CHANGE = 3
INSUFFICIENT = 1
```

Из этих 8 наблюдений запрещено делать выводы вида:

- «общая AI-видимость сайта = X»;
- «сайт стабильно виден/не виден в AI»;
- «GenSearch = ответы consumer Alice»;
- «AI доказал влияние на лиды/продажи»;
- «источник выше в списке = выше ранжируется».

Семь кейсов имеют single-snapshot temporal state; один был повторён в коротком окне. Это не longitudinal study.

## Почему нет новых страниц и destructive actions

После current-site reconciliation финальная Search-архитектура имеет:

```text
SUPPORTED NEW PAGE ACTIONS = 0
SUPPORTED DESTRUCTIVE ACTIONS = 0
```

Это не означает «новые страницы никогда не нужны». Это означает только, что в текущем принятом evidence set ни одна новая/удаляющая операция не получила достаточного основания, а ряд ранее считавшихся отсутствующими страниц был найден при свежей проверке сайта.

## Как читать P1 / P2 / P3

Это **аналитический порядок важности**, а не календарь производства.

```text
P1 = наиболее важный аналитический слой по доступным доказательствам
P2 = следующий слой важности
P3 = более поздний аналитический слой
HOLD = решение заблокировано конкретной неизвестностью
```

Для 92 исполнимых work packages в текущем заказе нет подтверждённых:

- execution owner;
- effort;
- capacity;
- delivery window.

Поэтому:

```text
EXPECTED IMPLEMENTATION PRIORITY = PENDING_CALIBRATION
FINAL SPRINT/CALENDAR SCHEDULE = NOT READY
```

Нельзя читать P1 как «обязательно положить в первый sprint» без реальной оценки исполнителя.

## HOLD

HOLD не означает «плохая идея», «низкий спрос» или «не делать».

HOLD означает: для конкретного unit не хватает названного business/evidence/policy fact. В Step18 20 таких units разложены на 20 отдельных recheck packages.

## Измерение после внедрения

Step18 определил 7 классов проверки результата:

- owner/role correction;
- overlap differentiation;
- content enhancement;
- bounded AI-content recheck;
- internal-link implementation;
- route-to-existing implementation;
- HOLD/recheck.

Важно:

```text
RECHECK TRIGGER != SUCCESS METRIC
```

Сначала нужно проверить, что изменение физически внедрено и соответствует принятой роли. При наличии будущих first-party данных Webmaster/Metrika можно дополнительно оценивать impressions, clicks, CTR, positions, visits, conversions и другие подходящие показатели — но эти данные **не наблюдались сейчас** и поэтому не представлены как текущий результат.

## Что работа не гарантирует

Нет гарантий:

- позиций в Yandex;
- трафика;
- лидов;
- конверсии;
- выручки;
- попадания/цитирования в Alice или иной AI surface.

## Текущая свежесть сайта

Step14A выполнил отдельную current-site reconciliation: 2683 public main-host URLs были обнаружены в durable recursive pass, 2624 URL вне прежнего upstream set классифицированы, 21 оказался архитектурно material, а material crawl errors были отдельно подтверждены. Это существенно снижает риск рекомендаций на основе старого инвентаря, но не является математическим доказательством существования абсолютно каждого возможного URL.

## Что нужно для production-ready implementation schedule

Чтобы превратить аналитическую очередь в реальный production roadmap, клиент/исполнитель должен добавить по пакетам как минимум:

1. кто отвечает за внедрение;
2. реальную оценку трудозатрат;
3. доступную capacity;
4. технические/редакционные зависимости;
5. при необходимости внутренний business priority;
6. способ и окно измерения результата.

Только после этого можно честно выпускать sprint/calendar sequence.
