## 1. What the client buys

MK01 is a standalone Yandex semantic-research product for an **existing public website**.

The client buys:

```text
AGREED BUSINESS SCOPE
→ YANDEX WORDSTAT DEMAND ACQUISITION
→ CLEANING / RELEVANCE CLASSIFICATION
→ PRESERVED UNCERTAINTY
→ TARGETED YANDEX SEARCH CHECKS ONLY WHERE A MATERIAL SEMANTIC BOUNDARY REQUIRES THEM
→ TASK/INTENT-BASED CLUSTERING
→ CLIENT-READABLE SEMANTIC CORE DELIVERABLE
```

Plain-language promise:

> Соберу поисковые запросы по согласованным направлениям существующего сайта, проверю спрос через Яндекс Wordstat, удалю подтверждённый мусор, отдельно сохраню спорные запросы и сгруппирую рабочую семантику по смыслу и задаче пользователя. Где одной формулировки недостаточно для надёжного решения, использую точечную проверку обычной выдачи Яндекса.

The deliverable is **not merely a parser export** and **not merely a final flat keyword list**. It contains both a working spreadsheet and an evidence-backed analytical explanation of what the research showed.

## 5. Base-scope work included

### 5.1. Scope and business freeze

Before provider acquisition:

- freeze the exact site;
- freeze the primary region;
- freeze products/services/directions included in the order;
- freeze known exclusions;
- distinguish public business facts from internal client priorities;
- record unresolved client facts rather than inventing them;
- freeze purchased governed-phrase and Search capacity.

### 5.2. Current-site / business model

Read the current public website sufficiently to understand what the business actually offers and what vocabulary/taxonomy already exists.

The site model is evidence for scope and clustering. It is not assumed to be complete or permanently current merely because one discovery pass succeeded.

### 5.3. Seed / acquisition plan

Build bounded Wordstat probes from the agreed scope.

Canonical boundary:

```text
SEED != FINAL KEYWORD
CURRENT SITE TAXONOMY != AUTOMATIC FINAL SEMANTIC TAXONOMY
```

A seed exists to discover demand vocabulary, not to pre-approve phrases.

### 5.4. Yandex Wordstat acquisition

Acquire demand evidence under the approved KW-001 durability rules.

The reusable dataset must preserve returned occurrence/provenance fields needed to answer, where supplied/defined:

- exact phrase;
- observed count;
- returned-row role/type;
- seed/request lineage;
- region/region ID;
- device/operator mode when applicable;
- acquisition time;
- provider/request/source identity;
- raw or durable raw-equivalent evidence;
- truncation/completeness state when available.

Provider success alone is not completion. Data must be persisted and reconciled.

### 5.5. First triage and targeted expansion

Remove obvious out-of-scope/noise families conservatively.

A second acquisition is allowed only when a named unresolved information gap justifies it. It is not an automatic recursive expansion loop.

### 5.6. Competitor expansion boundary

**Step5A competitor semantic expansion is NOT included in the MK01 base scope.**

Reason: the mini-kwork series has a dedicated competitor/gap product (MK03). Including Step5A silently in MK01 would blur product boundaries and give away a separately sellable research layer.

```text
MK01 BASE = NATIVE YANDEX DEMAND ACQUISITION + CLEANING + CLUSTERING
MK03 = COMPETITOR-DERIVED SEMANTIC GAP RESEARCH
```

### 5.7. Row-level semantic cleanup

Every phrase inside the purchased/frozen governed review set must receive an explicit state/reason.

Canonical boundaries:

```text
NO REJECTION RULE MATCHED != KEEP
LOW FREQUENCY != IRRELEVANT
HIGH FREQUENCY != RELEVANT
ASSOCIATION/VOLUME != BUSINESS FIT
```

Positive semantic/business evidence is required for KEEP. Potentially useful ambiguity remains REVIEW / deferred / Search-required rather than being forced into the active core.

### 5.8. Search-stage freeze

Preserve active, review, deferred and excluded states without silent drops. Every governed phrase must retain deterministic demand/provenance traceability.

Search routing is allowed only when there is a real Search-resolvable question.

### 5.9. Targeted ordinary Yandex Search checks

Ordinary Yandex Search is used only for decision-relevant semantic/intent/compatibility boundaries that cannot be safely resolved from preserved evidence alone.

MK01 does not promise exhaustive rank tracking or a bulk SERP audit.

Canonical scope rule:

```text
EXACT QUERY OBSERVATION != UNPROBED QUERY EVIDENCE
EXACT QUERY OBSERVATION != WHOLE-FAMILY PROOF WITHOUT DECLARED GENERALIZATION
```

Base V1 includes up to 40 justified exact-query checks. Unused capacity is not fake work. Additional justified ambiguity follows the Search add-on or remains explicit review/deferred.

### 5.10. Clustering

Group accepted/active phrases by the current-domain task/intent/result compatibility required by this product.

Default principle:

```text
SAME MATERIAL USER TASK -> SAME CLUSTER CANDIDATE
MATERIAL USER-TASK DIFFERENCE -> SPLIT CANDIDATE
UNCLEAR BOUNDARY -> REVIEW / APPROVED EVIDENCE ROUTE
```

No fixed cluster count is invented merely for a tidy report. Local domain rules are allowed only when scoped to the current job and supported by current evidence/constraints.

## 6. Exact base deliverable classes

The standalone MK01 client result contains:

### A. Seven-sheet semantic-core XLSX

The workbook contains the full governed set, working core, semantic groups, review set, excluded set, methodology and usage instructions. See `DELIVERABLE_SPEC.md`.

### B. Cluster map

For every final material cluster the client can understand its human-readable name, task/meaning, member count, representative phrases and important boundary notes.

### C. Exclusion/review ledger

Rejected or uncertain demand does not disappear silently. The client can see what was excluded/deferred and why.

### D. Methodology and limitations

Explain in normal client language:

- that demand comes from Yandex Wordstat;
- that ordinary Yandex Search is used selectively for disputed semantic boundaries;
- what region/scope was researched;
- what is and is not covered;
- that Google is outside the product;
- that private Yandex access is not required for the base result.

### E. Mandatory analytical client PDF report

A concise report governed by `CLIENT_REPORT_SPEC.md` explains **what the research showed**, not only what work was performed. It includes evidence-backed executive findings, current demand/task structure, material semantic groups, uncertainty/exclusion analysis, XLSX usage, Wordstat limitations, Yandex-only scope and reasonable next steps.

There is no fixed page-count PASS requirement. Report length follows current evidence and recipient task.

### F. Short handoff message

A short Kwork/chat message attaches both XLSX and PDF and explains which file to open first. It is not a separate TXT report.

The validated physical base package is therefore: **one standalone seven-sheet XLSX + one analytical client PDF report + a short handoff message in the marketplace/chat**. Full audit sidecars remain internal unless separately required. See `DELIVERABLE_SPEC.md`, `CLIENT_REPORT_SPEC.md` and `PRODUCT_PACKAGING.md`.
