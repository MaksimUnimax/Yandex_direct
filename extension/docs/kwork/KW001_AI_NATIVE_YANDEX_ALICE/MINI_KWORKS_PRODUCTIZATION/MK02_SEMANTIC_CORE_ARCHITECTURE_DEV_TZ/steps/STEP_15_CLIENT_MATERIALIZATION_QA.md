# MK02 STEP 15 — CLIENT MATERIALIZATION / FINAL QA / READBACK

## PURPOSE
Turn current accepted semantic/page/architecture/action authorities into a complete client package that can be used without repository knowledge and prove that analytical and implementation views agree.

## WHY THIS STEP EXISTS
KW-001 repeatedly showed that correct databases/counts can still produce an unusable recipient artifact, and that a polished report can still fail if it only narrates the research process or leaves implementation analysis to the client. Report generation must not become hidden new research.

## INPUTS
Final accepted semantic core; cluster authority; phrase→page ownership; current-vs-target architecture; action/work-package authority; clarification/no-change/HOLD states; evidence/limitations; current product delivery contract.

## REQUIRED EVIDENCE
Current-authority materialization manifest; source revision identities; stable join keys; required client views; current action readiness states; recipient language; current market/product scope; generation code/version when physical files are built.

## METHOD
Freeze the logical and physical delivery contract **after the MK02 rehearsal proves the useful recipient form**, not before. Client artifacts are generated views of current authority, never competing truth.

At minimum the package must materialize equivalent logical views for:

1. semantic core / clusters;
2. phrase/task → current primary page ownership;
3. family owner/supporting page distinction where material;
4. current-vs-target architecture;
5. READY implementation specifications;
6. concrete clarifications/checks before implementation;
7. semantic-mapping/no-site-change/HOLD results;
8. relevant page-to-page relationships;
9. analytical explanation of material findings;
10. implementation acceptance/check method.

### Analytical report rule

```text
CLIENT ANALYTICAL REPORT != EXECUTION PROTOCOL
CORRECT COUNTS + CLEAN LAYOUT != RECIPIENT VALUE
```

The analytical layer explains what was learned about demand, page responsibility, current-vs-target architecture and material unresolved boundaries. It does not lead with provider calls, internal stages or QA history.

### Implementation report/TZ rule

The implementation layer is action-first:

```text
WHAT TO DO
WHY
WHERE
HOW WHEN RESOLVED
WHAT TO CLARIFY WHEN NOT RESOLVED
HOW TO CHECK THE FINISHED STATE
```

READY items are action-specific, not cloned templates. Topic→page and page→page tables must explain what they show, why they matter and how to use them. Internal action IDs/files/QA enums remain out of ordinary client prose.

### No report-stage research

```text
REPORT MATERIALIZATION != NEW PROJECT RESEARCH
```

If current research lacks exact placement, business fact, classification or other readiness evidence, materialization does not silently reread/research to upgrade the item. Move it to a concrete clarification/check unless a separately authorized research/revalidation task is opened.

### Recipient-language rule

Russian client-facing headers, statuses and explanations. Technical IDs may remain only as clearly secondary audit fields where useful.

### Physical QA

For every delivered XLSX/DOCX/PDF or equivalent:

- open/read actual final file;
- render/inspect representative/full views as appropriate;
- verify required tables/sections/filters/layout;
- reconcile counts/IDs/relationships to canonical authority;
- inspect every final PDF page when PDF exists;
- test recipient tasks rather than only file existence.

## OUTPUTS
Final client package; materialization manifest; analytical + implementation QA; physical/visual QA; recipient review; persistence/readback receipt.

## SOURCE KW-001 AUTHORITY
`STEP_19_CLIENT_DELIVERABLE_PACKAGING_METHOD.md`; Step20 report-specific acceptance gates; `STEP_20_REPORT_02_SPECIALIST_IMPLEMENTATION_GUIDE_GATE.md`; MK01 client-report E38/E39 correction.

## KNOWN FAILURE CLASSES
S20–S31; Report №02 failures A–U; stale generated view; partial correction propagation; report materialization triggering unauthorized new research.

## ROOT CAUSES
Repository completeness, file existence, polished layout and template regularity were mistaken for recipient usefulness and implementation completeness.

## NON-REPEAT CONTROLS
Current-authority manifest; one canonical truth feeds all views; forward/cross-reconciliation; analytical report “what did we learn?” gate; action-first implementation report; no internal process narration; no profession-first document identity; no fixed page-count quality proxy; no report-stage project research; render/recipient review; source/generator fix before final artifact.

## CLAIM BOUNDARIES
Client artifacts show supported Yandex semantic/architecture/implementation findings only. No Google, AI/Alice, competitor-gap completion, implementation completion, production schedule or guaranteed SEO outcome is implied.

## UNKNOWN / BLOCKER BEHAVIOR
Missing physical format decisions before rehearsal are acceptable at Level 1; missing logical client view is not. After the rehearsal freezes the delivery contract, any absent required physical artifact blocks release. Unresolved research remains visible as clarification/HOLD, not silently resolved during packaging.

## PASS GATE
All promised logical views materialized; counts/joins/relationships reconcile; READY states match Step14; no stale/superseded authority leakage; analytical report explains material findings; implementation report gives usable actions/clarifications; internal jargon leakage=0; placeholders=0; physical files usable; recipient can explain what to do/why/how/what remains unresolved; persistence/readback recorded honestly.

## CLIENT-FACING MEANING
«На выходе клиент получает не набор внутренних таблиц, а согласованный пакет: что показало исследование, какая структура сайта нужна, какие изменения уже можно внедрять, какие вопросы ещё нужно уточнить и как проверить результат после доработки.»
