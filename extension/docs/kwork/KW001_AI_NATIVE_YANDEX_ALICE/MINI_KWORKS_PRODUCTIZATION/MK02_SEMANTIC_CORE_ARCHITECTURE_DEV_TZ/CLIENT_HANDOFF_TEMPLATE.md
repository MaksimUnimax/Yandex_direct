# MK02 — CLIENT HANDOFF TEMPLATE

Status: **PHASE 6 PACKAGE AUTHORITY / TO BE PHYSICALLY VALIDATED IN PHASE 7**

Назначение: короткое сообщение клиенту при передаче результата MK02. Это не отдельный клиентский файл и не замена отчётам.

## Базовый шаблон

Здравствуйте.

Готов результат по семантическому ядру, SEO-структуре сайта и ТЗ на доработку под Яндекс.

В заказе три файла:

1. **`RESEARCH_AND_ARCHITECTURE_REPORT_<CLIENT_OR_DOMAIN>_<YYYY-MM-DD>.pdf`** — начните с него. Здесь коротко объяснено, что показало исследование спроса, как распределены основные поисковые задачи, что обнаружено по текущим страницам и какая поисковая структура подтверждена.
2. **`SEMANTIC_CORE_AND_SEO_STRUCTURE_<CLIENT_OR_DOMAIN>_<YYYY-MM-DD>.xlsx`** — рабочая книга со всеми запросами, группами, картой «запрос/задача → страница», текущей и целевой структурой, деталями решений, проверками и статусами.
3. **`SITE_IMPROVEMENT_TZ_<CLIENT_OR_DOMAIN>_<YYYY-MM-DD>.pdf`** — отдельное ТЗ по изменениям сайта. В начале находятся действия, которые уже можно передавать на внедрение; далее отдельно указано, что требует конкретного уточнения, повторной проверки или вообще не требует изменения сайта.

Рекомендуемый порядок:

**сначала аналитический PDF → затем лист «Начните здесь» в XLSX → затем PDF с ТЗ.**

Статусы в ТЗ важны: пункт со статусом «нужно уточнение / перепроверка / HOLD» нельзя выполнять как готовую рекомендацию, пока не получен указанный недостающий факт.

Работа выполнена для экосистемы Яндекса. Google, отдельное конкурентное расширение семантики и анализ Алисы/Яндекс Нейро в базовый MK02 не входят.

Результат не является гарантией роста позиций, трафика или продаж; он фиксирует доказанную карту спроса, владельцев страниц, целевую поисковую структуру и действия, которые следуют из текущих данных.

## Правила заполнения перед отправкой

Перед передачей клиенту:

- заменить `<CLIENT_OR_DOMAIN>` и `<YYYY-MM-DD>` на реальные имена файлов;
- не вставлять внутренние MK02/Stage/Step/QA identifiers;
- не вставлять git commit/hash, provider chronology или repository paths;
- если в заказе нет READY действий, не писать, что они есть — описать фактический результат;
- если есть business/placement/recheck/HOLD, сохранить эти ограничения в сообщении и документах;
- не обещать сроки внедрения, исполнителя или uplift, если они не являются отдельным подтверждённым входом;
- убедиться, что перечислены ровно те три файла, которые реально приложены.

```text
+ IMPLEMENTATION-TZ PDF EXPLAINED

+ NO INTERNAL REPOSITORY LANGUAGE
+ NO GUARANTEED UPLIFT
= HANDOFF MESSAGE PASS
```
