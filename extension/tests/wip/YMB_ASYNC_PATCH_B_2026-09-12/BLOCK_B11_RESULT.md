## Что добавлено

Команда `normalizeSaved` обрабатывает ровно один сохранённый item по jobId/index. Используется существующий runtime/normalizer. Нет POST/GET, новой покупки поиска, обнуления бюджета или подмены исходного ответа текстом из чата. Команда не принимает rawData, queryText, URL, credentials и количество элементов.

Сохранённый корректный ответ с прежним PARSE_FAILED может быть разобран текущим normalizer. Если сам исходный XML повреждён, повторный разбор честно остаётся ошибкой; никакого восстановления недостающей выдачи из предположений нет. Исходный raw остаётся прежним. Повтор успешно разобранного item не переписывает результат и revision.

Проверены также RESULT_SAVED, отсутствующий/неподходящий item, чужой владелец, Manual off, одновременные клики, отказ outbox после локального разбора и последующее восстановление без provider replay.

## Какие ошибки пакета исправлены

1. Успешно полученный Search-ответ с предупреждением об ошибке учёта терял stop_required. Пакет мог перейти к следующему pending item. Теперь результат сохраняется, job ставится на паузу и nextN не берёт следующую фразу.
2. Та же остановка не доходила до пакетного Autorun. Теперь run запрашивает паузу; после подтверждения доставки следующая автоматическая команда не отправляется.
3. Ошибка записи результата после выполненного fetch могла вернуть «запрос не выполнялся». Теперь сохранён подтверждённый либо неизвестный исход, а durable REQUEST_STARTED не превращается в разрешение повторить отправку.
4. Ошибка записи перед вторым запросом теряла сведения об уже выполненном первом. Итог и outbox теперь сохраняют правильное число подтверждённых обращений. Первый сохранённый результат не удаляется.

Ни один из этих сценариев не объявляется воспроизведением прежнего OOM компьютера владельца.

### RED/GREEN и ошибка тестового предположения

Новая команда отсутствовала в B10: 9/15 PASS, 6 FAIL; после добавления те же 15 проходят. Это отсутствие новой функции, не шесть независимых старых багов.

Финальные 12 batch/Check assertions против неизменённого B10: 8 PASS / 4 FAIL. Против B11: 12 PASS / 0 FAIL. Четыре product FAIL соответствуют перечисленным stop/receipt сценариям.

В первом черновом тесте ошибочно ожидалось, что подтверждённая кнопка Check obey Manual allowed_methods. По существовавшему принятому контракту Check специально может проверять невалидный ключ при выключенном Manual. Исправлено тестовое ожидание, production Check не изменён. Добавлен отдельный настоящий тест отказа записи admission до fetch. Исходный черновой журнал сохранён и не скрывается, но этот FAIL не считается product bug.
