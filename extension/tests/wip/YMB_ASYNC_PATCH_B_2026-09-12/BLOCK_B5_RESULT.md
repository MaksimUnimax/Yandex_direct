## 2. Что реализовано

### Общий транзакционный учёт

B5 `search_async_policy.js` расширяет B4: обычный Search, GenSearch, deferred submit и получение Operation используют одну процедуру резервирования в пределах закреплённого бюджета. Разные псевдонимы одного run не создают разные бюджеты. Старые расходы учитываются один раз при привязке; последующее чтение отображаемых счётчиков не добавляет их повторно.

Отдельная запись попытки сохраняется вместе с резервом и временем следующего разрешённого обращения. Получение Operation не считается новым платным Search. Неизвестный исход платного обращения не освобождает резерв и блокирует следующую платную отправку. Повтор settlement не делает повторного списания/возврата. Старые записи B4 без схемы B5 не стираются и не допускаются молча: требуется отдельное решение миграции.

### Подключение к фактическому старому отправителю

Новый `search_legacy_admission.js` и точный delta `shared/phase3_provider_runtime.js` добавляют hook непосредственно перед прежним fetch. Само тело обычного provider-запроса/разбора сохраняется. При включённом guard отказ не вызывает fetch. После ожидания локального допуска перепроверяются контекст и credentials; изменившийся ключ не отправляется.

Ожидание ограничения скорости ограничено временем до 5 секунд и максимум тремя проверками локального допуска. Это НЕ повтор provider-запроса: callback отправки вызывается не более одного раза. Сбой учёта после получения ответа не уничтожает сам ответ: возвращается предупреждение остановки, а незакрытый резерв не пропускает следующую отправку.

### Старые счётчики и credential Check

Точные изменения четырёх legacy-файлов сохранены в `evidence/B5_LEGACY_DELTA.diff`: `service_worker.js`, `wordstat_batch_worker_integration.js`, `search_batch_worker_transport.js`, `shared/phase3_provider_runtime.js`.

При активном Search guard убран только старый предварительный прирост оплачиваемых запросов/стоимости. Счётчик попыток, состояние requesting и идентификатор worker сохранены. Версионированное отображение итогов не перезаписывает другую сессию и не принимает устаревшие значения поверх новых.

Отдельно сохранён штатный подтверждённый Search credential Check. Он может проверить ранее невалидный ключ при отключённом Manual, но только после прежнего явного подтверждения платного Check. Признак разрешения передаётся приватным Symbol из самого Check-кода; строка в metadata не подменяет это разрешение. Чужие сервисы через Search guard не проходят.

## 3. Что ещё НЕ подключено

`YMBSearchAdmissionGuard` пока создаётся в тестовой связке, не в production bootstrap. Реальный доверенный resolver владельца/run/Manual из worker ещё необходимо реализовать и проверить. Нельзя принять metadata из чата за такой resolver.

То есть общий атомарный механизм и hook старого отправителя написаны и проверены на перечисленных сценариях, но полная интеграция всех способов запуска ещё НЕ принята. Обязательны: активация guard в правильном порядке; запрет deferred при неготовом guard; actual worker/message ownership; восстановление run; реакция старых циклов на остановку учёта; общий бюджет при сменах настроек/сервисов; связка с B3/B4 и Patch A.

Никаких изменений установочного manifest, нового ZIP или принятой сборки в B5 нет.

## Простыми словами

Обычный и отложенный поиск теперь могут получать разрешение из одного учёта, а не независимо тратить один и тот же остаток. Старый отправитель подключён к этому механизму в проверяемом кандидате; повторного списания и потери счётчика попыток в проверенных случаях нет. Все изменения и исполняемые тесты сохранены. Следующий шаг — включить это в настоящую worker-цепочку. Без проверки памяти и всей объединённой сборки ZIP владельцу не выдаётся.
